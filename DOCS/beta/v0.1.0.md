# v0.1.0 — Durcissement sécurité

> **Date** : 11 août 2026
> **Phase** : beta
> **État** : livrée côté code — ⚠️ **règles Firebase à publier manuellement**

---

## Résumé

Fermeture des failles de sécurité du projet : le back-office `/admin` était accessible sans authentification, et les règles Firestore laissaient n'importe quel utilisateur s'auto-promouvoir administrateur.

Cette version débloque aussi le build, qui échouait sur 11 erreurs de typage antérieures.

---

## Contexte

Un scan de dépendances a signalé 9 vulnérabilités et un score de 45/100. L'audit manuel qui a suivi a montré que **le classement du scanner était inversé** :

| Ce que le scanner disait | Réalité vérifiée |
|---|---|
| 5 vulnérabilités HIGH sur `next` | ✅ Vrai — et pire : **22 advisories**, pas 5 |
| 3 secrets en dur dans le code | ❌ Faux — `firebaseconfig.ts` lit `process.env.*`, aucun secret trouvé |
| 1 fuite mémoire critique | ⚠️ Très exagéré — 1 timer non nettoyé, sans impact réel |
| *(rien)* | 🔴 **`/admin` ouvert à tous** — la seule faille réellement exploitable |

Le scanner n'analysait que `package.json`. Il n'a vu ni le contrôle d'accès manquant, ni les règles Firestore.

## Changements

### T1 — Typage du rôle utilisateur

Le champ `role: "user"` était déjà écrit à l'inscription ([signin.ts:70](../../src/lib/hooks/store/auth/signin.ts#L70)) mais n'existait pas dans les types.

- `src/lib/types.ts` — ajout du type `UserRole` et du champ `role` dans `UserProfile`
- `src/lib/hooks/store/useProfile.ts` — lecture du rôle avec défaut prudent `"user"`
- `src/app/(main)/feed/page.tsx` — `role: "user"` sur le profil de repli

### T2 — Réécriture des règles Firestore

Fichier : `FIRESTORE_RULES.md` (réécrit intégralement)

| Faille | Avant | Après |
|---|---|---|
| Auto-promotion admin | `allow write` sur tout le document user | `role` interdit à l'écriture |
| XP / niveaux / badges falsifiables | idem | `stats` interdit à l'écriture |
| Compteur de likes arbitraire | n'importe quelle valeur acceptée | delta de ±1 obligatoire |
| Usurpation de notification | `allow create: if request.auth != null` | `fromUid == request.auth.uid` |
| Commentaires bloqués | collection racine non couverte → default-deny | règles alignées sur le code |
| Modération impossible | suppression réservée à l'auteur | auteur **ou** admin |

**Bug de fond corrigé** : les anciennes règles utilisaient `request.resource.data.keys()` pour détecter les champs modifiés. Or `request.resource.data` est le document **après** écriture, pas le delta — les conditions `!('uid' in ...)` et `hasOnly([...])` ne faisaient donc pas ce que leur auteur croyait. Remplacé par `request.resource.data.diff(resource.data).affectedKeys()`.

### T3 — Contrôle d'accès `/admin`

- `src/lib/hooks/store/auth/useAdminGuard.ts` — **nouveau fichier**
- `src/app/admin/layout.tsx` — câblage du guard + écran de vérification

Comportement : pas de session → `/login` ; session non-admin → `/feed` ; erreur de lecture → `/feed` (on refuse en cas de doute). Aucun contenu admin n'est peint avant confirmation du rôle.

> ⚠️ **Ce guard n'est pas une sécurité.** Il tourne dans le navigateur et reste contournable. La vraie frontière, ce sont les règles Firestore. Il empêche seulement d'afficher une interface à qui n'y a pas droit.

**Pourquoi pas un `middleware.ts` ?** Le SDK Firebase client stocke l'ID token en IndexedDB, pas en cookie : le middleware Edge ne peut pas le lire. Et `next@16.2.3` cumulait 5 CVE de contournement de middleware.

### T4 — Règles Firebase Storage

Fichier : `STORAGE_RULES.md` — **nouveau**

Les validations de `storage.ts` (5 Mo, JPEG/PNG/WebP) s'exécutaient uniquement dans le navigateur. Elles sont désormais rejouées côté serveur : chemin réservé au propriétaire, taille, `contentType` en liste blanche.

### T5 — Compteurs atomiques

Fichier : `src/lib/hooks/store/usePost.ts`

Avant, `toggleLike` faisait un read-then-write : deux likes simultanés n'en comptaient qu'un, et la valeur finale était choisie par le client.

- `increment(1)` / `increment(-1)` au lieu de `currentLikes + 1`
- `writeBatch` : le document de like et le compteur partent dans la même écriture atomique
- `addComment` incrémente désormais `stats.comments` (ce n'était pas fait)
- Suppression d'une lecture Firestore inutile par like

### T6 — Dépendances

Fichier : `package.json`

- `next` : `^16.2.3` → `^16.3.0`. La plage vulnérable s'arrêtait à `16.3.0-preview.10`, la stable 16.3.0 est hors périmètre. Le plancher est verrouillé pour qu'un `npm install` ailleurs ne retombe pas sur une version faillible.
- `shadcn` et `herozion` déplacés de `dependencies` vers `devDependencies` — ce sont des CLI, aucun code applicatif ne les importe. `shadcn` traînait `@modelcontextprotocol/sdk` → `@hono/node-server` dans l'arbre de production.

**Résultat : `npm audit` passe de 19 vulnérabilités (2 critical, 10 high) à 0.**

### T8 — Déblocage du build

Le projet ne compilait pas : 11 erreurs de typage antérieures bloquaient `npm run build`.

| Fichier | Correction |
|---|---|
| `src/lib/types.ts` | `followersCount` / `followingCount` ajoutés en optionnels à `ProfileStats` |
| `src/app/(main)/settings/page.tsx` | `saveProfile` → `handleSubmit` (le nom réellement exposé par `useProfile`) |
| `src/components/main/sidebar.tsx` | `SidebarProps` accepte `isExpanded` et `onToggle` ; `iconOnly` en est déduit |
| `src/components/features/search/AnimeCard.tsx` | `import "next/image"` → `import Image` ; `<image>` (élément SVG) → `<Image fill sizes>` |
| `src/lib/hooks/store/auth/useLogin.ts` | `FirebaseError` importé depuis `firebase/app`, pas `firebase/auth` |
| `src/lib/hooks/store/useXPSystem.ts` | `XP_REWARDS` typé `Record<XPReward["type"], number>` au lieu de `Record<string, number>` |
| `src/components/ui/button.tsx` | export nommé ajouté à côté du défaut ; extraction de `buttonClasses()` |
| `src/components/ui/alert-dialog.tsx` | adapté à l'API du Button maison |
| `src/components/ui/carousel.tsx` | idem |

**Deux points de fond :**

`AnimeCard` utilisait `<image>` en minuscules — l'élément **SVG**, pas une image HTML. React l'acceptait sans broncher côté JSX, mais l'attribut `src` n'existe pas dessus : l'image ne s'affichait pas.

`alert-dialog.tsx` et `carousel.tsx` sont du shadcn standard, écrits pour l'API shadcn (`variant="outline"`, `size="icon-sm"`, `asChild`) alors que `button.tsx` est un composant maison avec une API différente. Ils ont été adaptés (`ghost` / `sm` / `md`). Pour `alert-dialog`, le motif `<Button asChild>` a été remplacé par l'application directe de `buttonClasses()` sur la primitive Radix — envelopper la primitive dans un `<button>` aurait produit un bouton dans un bouton, donc du HTML invalide.

Ces deux composants ne sont importés nulle part pour l'instant.

### T7 — Timer non nettoyé

Fichier : `src/components/ui/Message.tsx`

Un `setTimeout` imbriqué n'était jamais annulé et pouvait appeler `onDismiss` après démontage. Suivi dans une `useRef`, nettoyé au démontage.

## Actions manuelles requises

🔴 **Aucune règle n'est active tant qu'elle n'est pas publiée.** Les tickets T2 et T4 ont produit des fichiers markdown — le déploiement se fait à la main dans la console Firebase.

**Dans cet ordre :**

1. **Firestore > Règles** → coller le contenu de `FIRESTORE_RULES.md` → **Publier**
2. **Storage > Règles** → coller le contenu de `STORAGE_RULES.md` → **Publier**
   ⚠️ Vérifier d'abord le chemin réel des médias de post (supposé `posts/{userId}/{fichier}`), sinon la création de post cassera avec `storage/unauthorized`
3. **Firestore > `users` > son propre document** → passer `role` de `"user"` à `"admin"`

L'ordre compte : publier les règles **avant** de se promouvoir. Et c'est volontairement manuel — aucune règle ne permet d'écrire le champ `role`, car si l'application pouvait créer un admin, un attaquant le pourrait aussi.

## Dette connue

### 🟠 `onToggle` de la sidebar n'est pas câblé

`AppLayout` passe `onToggle={() => setIsMenuOpen(false)}` au `Sidebar` du menu mobile, pour fermer le menu quand on clique un lien. La prop est désormais acceptée par `SidebarProps` (ce qui débloque le typage), **mais elle n'est branchée sur rien**. Le menu mobile ne se referme pas à la navigation.

### 🟠 L'XP n'est jamais sauvegardée

Dans [useXPSystem.ts:57-61](../../src/lib/hooks/store/useXPSystem.ts#L57-L61), l'écriture Firestore est en commentaire. Tout le progrès est perdu au rechargement de la page.

C'est ce qui a permis de verrouiller `stats` en T2 sans rien casser. **Quand cette fonctionnalité sera terminée, l'écriture devra passer par une Cloud Function** — si le client peut écrire son XP, la faille est rouverte.

### 🟠 `ProfileStats` a divergé du code

Le type déclare `xp`, `level`, `rank`, `badge` ; les pages profil utilisent `followersCount` et `followingCount`, qui n'existent nulle part. À réconcilier.

### 🟡 Lint global

59 problèmes au total (18 erreurs, 41 avertissements) sur l'ensemble du projet : entités non échappées, `setState` dans des effets, `prefer-const`, `any`. Aucun introduit par cette version.

### ⚪ Limites assumées des règles

- **Pas de limitation de débit.** Un compte peut spammer commentaires et notifications — cela nécessiterait des Cloud Functions ou App Check.
- **`isAdmin()` coûte une lecture** par évaluation de règle. Acceptable au volume actuel ; passer aux custom claims si nécessaire.
- **Le like reste manipulable à la marge** : un client peut envoyer +1 sans créer le document `likes` correspondant.
